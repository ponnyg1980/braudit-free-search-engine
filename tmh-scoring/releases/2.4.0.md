# tmh-scoring 2.4.0 — labelled sensitivity steps

**Released** 21 September 2026
**Decision** H — sensitivity applied at Triage/Client Review (Jonathan, 20 Sep 2026)
**Band impact** ZERO DIFFERENCES — nothing in this release runs unless a step is set

---

## What changed

New module `tmh_scoring/sensitivity.py`: the table that turns a Triage control
position into a `ScoringSettings`.

```python
from tmh_scoring.sensitivity import settings_for
from tmh_scoring.two_layer import assess

assess(..., settings=settings_for({"phonetic": 1, "terms": -1}))
```

Five positions — **Much stricter (−2), Stricter (−1), Standard (0), More
sensitive (+1), Much more sensitive (+2)** — on each of six compartments.
Nobody in Triage types a number.

## Why the indirection

Triage picks a step; R&D owns what a step means. Those are different decisions
belonging to different people, and separating them is what makes the log worth
keeping. A run records the STEP it used and the `scoring_version` in force at
the time, so when R&D later re-tunes what "+1" means the history does not
silently rewrite itself: run 9270f8f3 was scored at "sounds like +1" under
tmh_scoring/2.4.0, and 2.4.0 is on disk saying exactly what that was.

It is also what keeps Triage away from the globals. The only thing Triage can
produce is a step per compartment; the only thing this module can produce is a
delta from `DEFAULTS` for one run. Moving `DEFAULTS` is a package release with
its own band_diff — R&D's, and Jonathan's.

## Step 0 is exactly DEFAULTS

Not approximately. `settings_for(None)`, `settings_for({})` and
`settings_for({c: 0 for c in COMPARTMENTS})` all return **the `DEFAULTS` object
itself**, not an equal copy, and the module asserts at import that every
compartment's step-0 preset is empty. A "standard" run must be bit-identical to
a run with no sensitivity at all, or Triage's clear path does not restore
anything — and clear is the dangerous operation this design has to get right.

## What a step does not touch

- **The measurements.** Edit distance, syllable splitting, Soundex, the
  overlap coefficient, the conflict matrix. Those are the model.
- **`generic_guard_ratio`** — the rule that stops SWIFT COURIERS and RAPID
  COURIERS resembling each other through the word they share. "More sensitive"
  must not mean "reintroduce the false positive the guard was written to kill".
- **`token_coverage_for_whole`** — whether a token speaks for a whole mark
  (SMARTCARD vs SMART) is a structural judgement, not a sensitivity one.
- **`goods_class_link_score`** — a fallback score assigned when there is no
  text at all, not a gate, so there is nothing to loosen.
- **Any other compartment.** `_validate()` runs at import and refuses a preset
  that sets a field belonging to another compartment. That is what makes a
  compartment a compartment, and the reason 2.3.0 had to split
  `mark_similarity`'s tier-3 gate across the three axes.

## Presets are values, not offsets

Written as explicit thresholds rather than arithmetic deltas. An offset table
looks tidier and is unreadable in an audit — "+1 means −0.04" tells nobody what
the threshold became. It also cannot handle a lumpy measure, and one of these
is very lumpy.

**Spelled like** is discrete. One edit scores 0.95, two edits on a long mark
0.90, two on a short one or three on a very long one 0.85, anything worse falls
through to a sequence ratio. So the gate only means something when it lands
*between* those values:

| gate | admits |
|---|---|
| 0.96 | identical only |
| 0.92 | one edit (VETSURA / VETSURE) |
| **0.90** | **+ two edits on a long mark — standard** |
| 0.85 | + two on a short mark, three on a very long one |
| 0.80 | + whatever the raw ratio gives |

A step at 0.88 would change nothing while appearing in the log as a change,
which is worse than not offering it.

## Not every compartment offers every step

`AVAILABLE_STEPS` is derived from `PRESETS`, so the two cannot drift, and
`normalise_steps` refuses a position a compartment does not offer.

**`classes` has no +2.** The standard already treats one shared class as a
trade overlap, so there is nowhere below it to go; the only remaining loosening
would be to call a single shared class a full tier-3 overlap, which class 35
on its own — advertising, business management and retail in one class — makes
indefensible. The control shows that position disabled rather than offering a
step that scores identically to +1 and logs as though something changed.

## Measured

`tools/sensitivity_sweep.py` (new) replays a band_diff inputs file at every
offered step and reports what moves. A preset table is an assertion until it is
measured; this is how a step that moves nothing gets caught before it reaches a
control.

**Watch, 12,000-record random sample (seed 7)** — % of records changing band:

| compartment | −2 | −1 | +1 | +2 |
|---|---|---|---|---|
| classes | 0.60% ↓ | 0.53% ↓ | **0.00%** | *not offered* |
| terms | 1.66% ↓ | 1.13% ↓ | 0.68% ↑ | 1.81% ↑ |
| phonetic | 0.17% ↓ | 0.17% ↓ | 0.20% ↑ | 0.92% ↑ |
| orthographic | 1.17% ↓ | 0.60% ↓ | 0.83% ↑ | 1.66% ↑ |
| fuzzy | 4.62% ↓ | 2.83% ↓ | 1.12% ↑ | 2.81% ↑ |
| visual | — | — | — | — |

**Audit, run 8ccac5ee, 1,164 records** — terms 0.43–1.63%, fuzzy 2.41–11.77%,
orthographic 0.09%, classes and phonetic 0.00%.

Read it as: **every step moves in the direction its label promises, and none of
them moves the report wholesale.** The largest single effect is fuzzy −2 at
4.6% of Watch rows and 11.8% of audit rows, all downward, mostly
Low/Medium → Low. That is a sensitivity control, not a different scorer.

Three entries need saying out loud rather than leaving in a table:

- **`visual` moves nothing anywhere, as expected.** The image scorer is built
  but not wired into any run. The steps exist so the compartment set is
  complete and the panel can render the control disabled. Phase 2.
- **`classes +1` moved nothing on either corpus.** It is not inert — it drops
  the tier-3 threshold from three shared classes to two — but rows with
  *exactly* two shared classes *and* no usable specification text either side
  are rare. It stays, because that client exists; it is flagged here so nobody
  reads a future 0% as a bug.
- **`classes` and `phonetic` move nothing on the audit corpus** but do on
  Watch. That run has specification text on both sides, so the class-only
  fallback never fires, and it happens to contain no near-rhyme pairs where
  sound is the deciding axis. A corpus limitation, not a preset one — which is
  exactly why the sweep runs on both.

## For the app

`settings_for(steps)` is the only call the audit engine needs. Store the STEPS
on the run, not the thresholds: the steps are what a human chose, and
`deltas_for(steps)` recovers what the scorer actually did for the audit log.
Store the `scoring_version` alongside, because that is what makes the pair
readable later.
